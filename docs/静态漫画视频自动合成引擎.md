# 静态漫画视频自动合成引擎：技术设计 V2.0

> 修订日期：2026-10-21。本文为设计方案，尚未实现引擎或完成真实样片验收。
> 当前范围：每期开始先确认图片供应渠道，经本地工具生图、授权第三方图片检索或人工按提示词供图取得已批准原画，结合完整中文配音由 Python 编译时间线；Remotion 完成整片视觉动画，FFmpeg 完成音频母带与最终封装。字幕由用户后期制作。

适用流程：**创建项目并确认图片渠道 → 分镜确认与镜头级渠道分配 → 图片生成/合法检索/人工供图 → 人工逐图或按明确批次审核 → 完整配音对齐 → AI 依据已批准原画设计转场 → 锁定时间线 → Remotion 视觉渲染 → FFmpeg 合成完整配音 → 预览审核及成片验证**。

## 1. 目标与边界

### 1.1 首版范围

- 每镜头使用一张完整且通过审批的静态图片，支持本地生图、第三方合规检索、人工按提示词生图及逐镜头混合；Remotion 实现静止、缓慢推近、拉远、横向和纵向平移。
- 每个镜头边界依据前后叙事关系选择转场。Remotion 首版支持直接切镜、短叠化、自定义淡黑及左右方向擦除；允许全片使用有充分叙事依据的硬切，不设置特效配额。
- 使用一条已完成的旁白音轨，保留其内容、速度及头尾停顿。
- 语音识别和对齐只用于核对旁白与原文、辅助确定换图时刻，不要求为了字幕达到逐字呈现精度。
- Remotion 输出完整无声视觉轨；FFmpeg 与未裁剪的旁白母带完成最终混流，输出无字幕视频，供用户后期制作。

本版包含图片供应渠道编排、已授权工具调用/检索、提示词交付、来源追溯及人工审图，不自研基础图像模型、通用爬虫平台或第三方图库服务。文案创作、配音生成、字幕文件/排版、背景音乐、多轨道编辑、人物口型、姿势替换和道具独立运动不在本版范围。


### 1.2 与仓库现有方案的关系

仓库根目录 `DESIGN.md` 所描述的 Remotion 分层动画路线，面向独立人物、道具和动态图解；本文使用同一视觉技术栈，但首版只绘制**整张静态插画**的镜头运动与转场。两套产品需求及素材协议各自独立，不以当前静态路线完成来声称分层动画目标已完成。

本次仅修订本文，作为未来静态漫画合成引擎实施依据；不修改已有仓库基线、不实施引擎代码或安装依赖。后续代码模块建议落在 `renderer/static-comic/`，由 Python 编排器调用，避免复制 Remotion 核心框架或预先设计多渲染器切换层。

### 1.3 输入契约和安全边界

- `input/script.txt`：已确认的中文旁白原文，仅用于内容核对、语音定位和转场语义决策。
- `input/storyboard.json`：有序镜头、原文字符区间、画面叙事说明、拟使用图像/资产 ID、运镜参数及经确认的语义转场计划。尚未取得图片时保留待供应状态，不能伪造审批。
- `input/voice.mp3` 或 `input/voice.wav`：一条完整已确认配音，是全片时长基准。
- `input/image_source_policy.json`：用户确认的单一/混合渠道政策及镜头级来源分配。
- `work/planning/image_requests.json`：每镜头配图要求、文生图提示词/检索条件、统一画风及目标文件路径。
- `assets/images/manifest.json`：已选资产的来源、许可、用途、版本、审核状态与哈希。
- `assets/images/shot_XXXX.png`：用于本期视频的目标正式图片路径；人工可先放入此路径，但需单独人工确认后才具备入镜资格。
- `input/render.yaml`：输出画幅、帧率、编码参数、预览规格、Remotion 渲染并发等受控数值。
- `input/overrides.json`：必要时人工确认读法、音频窗口或镜头边界；转场规划本身由 `storyboard.json` 统一维护。

`script_range` 使用**原始 Unicode 码点半开区间** `[start,end)`。源文案按 UTF-8 解码，移除可能存在的 BOM，但保留 CR/LF 等其他字符，不隐式转换换行；重复句不得以字符串 `find` 盲目定位。规范化文本另保存到原文区间的可逆映射；原文字节变化后旧范围、声学定位和批准记录均失效。

**输入路径安全：** 所有来自分镜的数据路径只接受本期 `content/<episode_id>/` 内受控的规范化相对路径；拒绝绝对路径、盘符、UNC、`..`、空路径、越界符号链接/Windows 联接点。实际读取前解析路径并检查真实文件类型、大小和解析后的目录归属；对输出目录重解析点同样检查。外部素材须先显式导入本期项目。

**Remotion 运行安全：** 浏览器运行时不得直接读取用户磁盘绝对路径，不通过任意 `file://` URL 加载源素材。Python 将审核通过的图片复制为不可变的、仅含可展示视觉资产的项目级 `work/remotion/public/images/`，校验暂存后哈希。首版不用硬链接共享可被修改的源文件，以免审核完成后原画变化影响浏览器预览；以 `--public-dir` 配合 `staticFile()` 加载。不得把原始旁白、原文或审核资料暴露到该公开素材目录，Studio 仅在受控本机环境运行。Python/Node/FFmpeg 进程均使用参数数组，禁止把模型文本拼接为 Shell 指令；React 组件仅接受 Schema 白名单数据，不执行 Agent 给出的代码。

### 1.4 输出契约

- `work/audio/master_48k.wav`：保留内容、头尾静音和时基的解码音频母带。
- `work/alignment/aligned.json`：原文、读法、粗识别、采样级时间证据与异常清单。
- `work/planning/transition_candidates.json`：AI 根据**已批准**的真实图片、口播和运镜生成的待审转场候选。
- `work/images/candidates/`：本地生图和第三方检索得到的待审候选图片；不得直接发布到 Remotion public。
- `work/timeline/timeline.lock.json`：逐帧权威时间线、输入摘要、转场预算及审核来源。
- `work/remotion/props.json`：经验证并编译的 Remotion 参数，不包含未授权绝对路径。
- `work/remotion/visual.mp4`：Remotion 渲染的**整条无声视觉轨**，视频帧数必须为 `T`。
- `preview/preview_visual.mp4`、`preview/preview.mp4`、`preview/contact_sheet.jpg`：同时间线的低清视觉预览、FFmpeg 叠加完整配音的有声预览、镜头联系表。
- `output/final.mp4`：默认 1920×1080、恒定 30 fps、H.264、AAC、`yuv420p`；**一条视频流、一条音频流、零字幕流**。
- `reports/validation.json`、`reports/render.json`：技术验证、版本、耗时、缓存与媒介哈希。
- `review/image_approvals.json`：逐镜头、逐哈希绑定图片来源与真实用户批准的审图收据。
- `review/approval.json`：最终有声预览批准收据，同时绑定本期使用的全部已批准图片及影响输出的输入摘要。

不创建 ASS、SRT、字幕流或后期排版数据。音频对齐只为镜头编排服务。


### 1.5 图片来源确认、混合供应与审核契约

**开工第一项操作：** 新建视频项目或接手尚未确认图片来源的项目时，Codex 必须向用户提供四种选择：① 本地工具生图 `agent_generate`；② 从许可明确的第三方网站/图库获得 `third_party_retrieve`；③ 由 Codex 给出详细提示词、用户手工生图并保存到规定目录 `manual_generate`；④ 镜头级混合 `mixed`。在用户明确选择前状态保持 `SOURCE_POLICY_PENDING`，不得自动生成或下载图片，也不得进入生产级视频渲染。有效且未发生变更的用户选择无需反复询问。

**镜头级计划：** 混合模式下，Codex 先按已确认分镜建议每一镜的供图渠道和图片要求；用户确认后才可批量执行。选定渠道不可用应报告 `UNAVAILABLE`，改用其他渠道或第三方提供者须获得用户同意。用户批准单个镜头采用另一渠道时，仅更新该镜头的分配及后续依赖。

**来源策略示例：**

```json
{
  "schema_version": "1.0",
  "mode": "mixed",
  "status": "APPROVED",
  "confirmed_by": "user",
  "shots": {
    "SHOT-001": "agent_generate",
    "SHOT-002": "third_party_retrieve",
    "SHOT-003": "manual_generate"
  }
}
```

其中 `confirmed_by`、实际批准时间、交互证据与策略哈希必须来自真实用户确认过程，示例仅说明结构。单一渠道模式使用相同的来源枚举以及 `default_channel`；任一待入镜镜头最终必须能够解析为唯一的供图来源。

三种来源都采用同一套图片要求与审批制度：

- **本地工具生图：** Codex 只调用当前确实可用且已获用户授权的生图工具；保存工具/模型及版本、完整中文提示词、参考图身份或画风版本、结果和图片 SHA-256。用户必须审查最终效果，工具调用成功不代表画面已批准。
- **第三方检索：** 优先使用合法图库接口或站点允许的下载机制，遵守访问限制与服务条款。每张候选保存来源 URL、作者、许可类型与证据、用途范围、必要署名、访问日期与文件哈希；版权或发布使用权不明确时进入待审核，不得默认为允许发布。不绕过访问/付费限制，不去除水印。`reference_only` 只作为有权使用的参考图，不直接进入视频；二次生成或加工必须检查授权与派生关系。
- **人工按提示词供图：** 每个镜头交付完整独立的中文文生图提示词及16:9画幅、画风锚定、人物一致性、镜头安全区、最小尺寸、命名和目标路径 `assets/images/shot_XXXX.png`。用户放图后进行格式、主体、安全区与哈希检查，再由用户明确确认采用；文件存在不代表批准。
- **混合模式的美术统一：** 图片可以来自不同渠道，但所有正式图片按同一风格规范、角色身份、构图要求和画面连续性检查。第三方素材不能满足二维漫画审美时，应作为合法参考或更换渠道；需要授权的编辑/再生成操作必须留存来源与再审批。

候选图片先写入 `work/images/candidates/`，终选图片记录到 `assets/images/manifest.json`，正式文件路径统一为 `assets/images/shot_XXXX.png`。图片状态包括 `PLANNED`、`WAITING_FOR_USER`、`CANDIDATE_READY`、`REVIEW_REQUIRED`、`APPROVED`、`REJECTED`、`UNAVAILABLE`。用户可单独或选定批次批准；`review/image_approvals.json` 绑定批准人、时间、镜头、渠道、许可、图片哈希。换来源、替换文件、修改字节或授权依据变化时，相应图片审批和转场视觉证据失效。

**生产门禁：** 只有本期全部入镜镜头的正式图片均有有效用户 `APPROVED` 收据，来源、许可、最终文件哈希匹配，才能进行正式 Remotion public 暂存、基于真实原画的 `TransitionPlanner` 以及有声预览或成片渲染。SC-P1/P2 允许使用明确标识的技术夹具验证渲染技术，不作为真实生产审批。

## 2. 技术选择与职责分工

| 模块 | 首版选择 | 唯一职责 |
|---|---|---|
| 总控 | Python 3.11+ | 项目校验、图片来源策略/审核状态、时间线编译、素材准备及调度 |
| 图片供应与溯源 | 已授权本地图像生成工具 / 合规图库检索接口 / 人工供图入口 | 分镜级来源选择、候选图、提示词、版权记录、用户审图与入镜批准 |
| 中文语音辅助对齐 | WhisperX 中文后端 | 粗识别、原文/读法映射、音频时间锚点和差异报告 |
| 语义导演 | Agent + TransitionPlanner | 结合原文、已生成图片、镜头运动与停顿生成转场候选 |
| 图像预处理 | Pillow | 校正方向、色彩、cover 裁切、主体框、图片暂存 |
| **整体视觉动画** | **Remotion + React + TypeScript** | 全片静态图片运镜、硬切、叠化、擦除、淡黑及预览 |
| 视觉编排组件 | `@remotion/transitions` | `TransitionSeries`、`fade`、`wipe`，淡黑采用受控自定义效果 |
| 音频与最终封装 | **FFmpeg + ffprobe** | 母带解码/重采样、完整配音混流、MP4 元数据与解码检查 |
| 验证与审核 | Python + ffprobe + Remotion Studio + 人工观看 | 时钟、帧数、画质、音画同步、语义和审核证据 |

**职责硬边界：** Codex 与适配器在用户授权渠道下准备图片，用户审批后交由 Python 锁定时间线；Remotion 编码无声 `visual.mp4`，FFmpeg 只负责音频与最终封装。首版不得在 FFmpeg 再次执行视觉转场，也不由 Remotion 合成最终旁白。图像生成/抓取工具的实际可用性必须检查，不能仅因为工作流声明了渠道就假定有执行权限。

首版固定 **30 fps**，`fps_num=30, fps_den=1`；时间线协议保留有理数帧率的公式，但在引擎支持非整数帧率通过端点测试之前拒绝此类配置。采用 Remotion 4 系列中锁定的确定版本；`remotion`、`@remotion/cli`、`@remotion/transitions` 及其他 `@remotion/*` 包必须保持版本一致，并锁定 Node.js、React、浏览器运行时、WhisperX、模型文件、FFmpeg 的版本或摘要。

Remotion 许可应根据实际使用主体、组织规模及是否向外提供自动化工具确认；不能默认所有商业自动化场景都属于免费许可。先完成环境与许可检查，再进入实际制作。

### 2.1 为什么不让 FFmpeg 执行运镜

原有 V1.2 的 `zoompan`、`xfade`、`concat` 组合能够完成基础视频，但混合转场需要维护视频滤镜图、PTS 与时间基兼容性。Remotion 的视觉组件直接以局部帧驱动，因此更便于预览和扩展。**音频对齐算法、重叠预算及帧数协议仍沿用**，只替换视觉执行层，不同时维护两套运镜实现。

### 2.2 端到端数据流

```text
口播文案 / 完整配音 / 已确认分镜
    ↓
用户确认图片来源策略 → 按镜头生图、合法检索或人工供图
    ↓
候选图审核、来源与许可核对 → 正式图片批准与哈希锁定
    ↓
Python：音频母带 + WhisperX 辅助对齐 + 人工边界校正
    ↓
AI：真实原画 + 上下文 + 镜头运镜 → 逐边界语义转场方案
    ↓
Python：timeline.lock.json（整数帧唯一执行依据）
    ↓
Python：图像预处理与项目级 Remotion public 目录暂存
    ↓
Remotion：整片运镜 + 语义转场 + 静态视觉预览
    ↓
work/remotion/visual.mp4（无声、完整 T 帧）
    ↓
FFmpeg：visual.mp4 + master_48k.wav（视频流复制）
    ↓
preview/preview.mp4 / output/final.mp4（完整配音、无字幕）
    ↓
ffprobe + 全片解码 + 人工试听/视觉审核
```

## 4. 时间线协议（V2.0）

保留 V1.2 的三层时钟：**语音语义锚点**决定意义何时出现，**逻辑边界**决定新镜头何时开始自身运动，**转场窗口**决定新图何时开始露出以及何时完全接替旧图。

`timeline.lock.json` 是不可由 AI 绕过的确定性执行输入。示例展示首镜头和从它出场的转场；其他镜头与哈希字段省略：

```json
{
  "schema_version": "2.0",
  "episode_id": "sample-001",
  "audio": {
    "source": "input/voice.mp3",
    "master": "work/audio/master_48k.wav",
    "sample_rate": 48000,
```

- Python 编译 `work/remotion/props.json` 时增加每镜头的 `head_hold_frames`、`logical_frames`、`tail_hold_frames`、`physical_frames`、`staged_image`，并验证 `sum(physical_frames)-sum(transition.duration_frames)=total_frames`；原始图片路径只用于安全读入与暂存，不暴露给浏览器。
- V2.0 协议在引擎正式实现前作为新基线，不需要对尚未实现的 V1.2 执行时旧协议构建复杂迁移层。未来若存在已入库旧分镜，再提供独立、显式、可审计的转换工具。

## 5. 配音处理、对齐与首版人工纠错

### 5.1 同源音频准备

来源音频先解码为 48 kHz WAV 母带，再从母带生成 16 kHz 单声道模型输入。两者保留相同起点、内容和停顿，不分别裁静音。

```bash
ffmpeg -y -i input/voice.mp3 -vn -ar 48000 -ac 2 -c:a pcm_s16le work/audio/master_48k.wav
ffmpeg -y -i work/audio/master_48k.wav -vn -ar 16000 -ac 1 -c:a pcm_s16le work/audio/align_16k.wav
```

时长以母带 PCM 采样帧数除以采样率计算。采样帧数指每个声道的时间位置数量，立体声不乘以 2。模型输入重采样产生的取整不改变母带时钟。

### 5.2 原文、读法与时间分别保存

1. 粗识别完整音频，得到分段文本和候选音频窗口；单人旁白不执行说话人分离。
2. 生成匹配用归一化文本，保留原文区间映射；使用有序匹配和分段锚点处理重复短句，不能只凭相似字符串选择位置。
3. 对数字、百分比、单位和缩写生成或人工确认实际读法，例如原文 `增长了28%`、读法 `增长了百分之二十八`。
4. 保存 `原文区间 ↔ 读法区间 ↔ 音频区间`，支持一对多、多对一。音频窗口及镜头锚点统一换算并锁定为 48 kHz 母带的整数采样位置；模型原始秒数与窗口来源仅保留为证据。将确认过且适合模型的读法送入声学对齐，不把数字原文直接当作等长发音单位。
5. 在可信短音频窗口内对齐，再恢复全局时间；明确窗口内时间与全局时间，防止重复加偏移。
6. 输出镜头边界所需的时间证据及原文/配音差异，标点不单独分配发音时间。

2026-10-21 核对的 WhisperX 官方源码为 `zh` 配置了 `jonatasgrosman/wav2vec2-large-xlsr-53-chinese-zh-cn`，并提供 `return_char_alignments=True`。实际实现以锁定版本为准。

**调用成功不是精确对齐成功。** 官方实现存在对齐失败后保留粗时间段，以及对部分缺失时间插值的处理。适配器必须检查原始字符结果、缺失项和失败情况，区分声学对齐、插值、粗分段、人工确认的来源；不得将插值或粗分段标为精确对齐。模型分数只作筛查证据，不解释为时间戳正确概率。

### 5.3 放行与异常规则

- 记录内容覆盖率、差异率、边界证据和异常定位。规范化字符匹配率 98% 可作为初始预警值，不能作为时间准确率或自动放行的唯一条件。
- 镜头边界必须单调、有可信时间或人工确认；缺失、零时长、不合理重叠和音频越界需报错或待审核。
- 首版关注换图时机，不要求每个内部字符达到逐字字幕精度。内部少量缺失若不影响内容核对及已确认边界，可记录后由人工确认；不能按平均字速补出虚假精度。
- 漏读、加读、重复句错配、截断或读法不明时，输出原文区间、候选音频窗口、受影响镜头和原因，进入 `REVIEW_REQUIRED`。
- 重对齐可复用未受影响窗口，但须确保音频、窗口内容、读法及模型版本相同；配音内容变化后不得直接沿用旧全局时间。

### 5.4 最小人工纠错入口

第一阶段即提供可编辑的 `input/overrides.json`，不以可视化时间轴为前提：

| 覆盖项 | 必须记录 | 效果 |
|---|---|---|
| 读法确认 | 原文区间、确认读法 | 重新映射并对齐受影响区域 |
| 音频窗口确认 | 原文区间、全局起止采样位置 | 限定可信窗口后重对齐 |
| 镜头边界确认 | 边界两侧镜头 ID、全局采样位置 | 生成标记为人工确认的边界 |

每项记录原因、操作者、时间及绑定的原文/配音/分镜摘要。摘要失效、覆盖冲突或边界越界时拒绝应用。相同覆盖重复运行得到相同结果，不改写原始模型输出。

若确认存在真实漏读，应修正源配音，或由用户明确修改原文与分镜；调整边界不能自动清除内容不一致。转场的语义、类型、时长和相对锚点位置在分镜中修订，避免与覆盖文件维护两套冲突参数；模型候选保留在工作目录，确认后再写入正式计划。修正后重编译时间线、重建受影响预览，再继续生产。


## 6. 镜头边界与整数帧时钟

每镜头的原文范围映射到语音区间；语音中的关键表达构成 `semantic_anchor_samples`。默认在下一段开口附近取逻辑边界 `B`，停顿分配给前镜头；允许因语义和镜头时机明确调整 `B`，但必须保存锚点、调整后的边界与理由。头部静音属于首镜头，尾部静音属于末镜头。转场的开始和完成时间由 `placement` 独立计算，不通过改变配音或悄悄挪动 `B` 实现。

设母带采样帧数为 `S`，采样率为 `R`，帧率为 `p/q`，总帧数用整数运算：

```text
T = (S*p + R*q - 1) // (R*q)
```

全局语义锚点、人工确认的边界先统一转换为母带整数采样位置 `s`，再按最近帧取整；非负值恰好半帧时向上：

```text
B(s) = (2*s*p + R*q) // (2*R*q)
```

模型浮点秒数转换为母带采样时，使用文档化的十进制/有理数读取与统一四舍五入规则，记录原始值、窗口全局偏移、转换后采样位置和精度来源；不得先截成整数毫秒再反复取整。`align_16k.wav` 的采样位置需按真实采样率和起点映射回母带，不直接混入 48 kHz 时间线。

首边界固定 0，末边界固定 `T`；先计算全部**绝对**边界再取差，避免逐段取整累计漂移。

- 逻辑镜头长度 `N_i = B_(i+1)-B_i` 至少 1 帧；转场容量不足时报告具体冲突，不静默缩短或移动边界。
- 视频时长为 `T*q/p`，满足 `0 <= T*q/p - S/R < q/p`。
- 不通过缩短、变速配音或丢弃末帧消除不足一帧的尾部差值。
- 最终解码帧数必须等于 `T`，仅比较容器时长不足以证明时间线正确。
- 语义锚点负责**旁白什么时候表达观点**，逻辑边界负责**新镜头何时开始自身运镜**，转场窗口负责**新图何时首次可见以及何时完整呈现**。三种时间均应在审核报告中可追踪。


## 7. Remotion 静态图片运镜

### 7.1 图片预处理、焦点与安全区

- 统一 EXIF 方向、ICC/sRGB、尺寸、方向、像素格式、色彩管理和透明通道处理；不合比例的原画先经可审查的 `cover` 裁切生成目标 16:9 图片，**不允许浏览器 `objectFit` 直接决定未经核验的随机裁切**。
- 原图应足以支持最终输出及最大推近倍数，例如 1920×1080 的最大推近 1.08 倍，建议预处理前原图至少约 2074×1167 像素；低于目标时标记画质风险，插值放大不创造细节。
- 预处理完成后，Remotion 使用**与画布同画幅**的图片填满整个元素；可设置 `objectFit: 'fill'`，此时它不会再改变预先确认的比例。
- `crop_anchor` 属于 **裁切窗口控制**，而不是“主角坐标”；必须标注的 `subject_bbox` 先映射到预处理后的图片坐标，再逐帧检查关键内容始终在可见范围内。
- 缩放为 1 时没有平移空间。编译器若发现 `z=1` 却要求非零视觉平移，必须拒绝或要求人工确认更大的源图/最小缩放；不得允许露出空白边缘。
- 缓慢运动容易暴露漫画的细线闪烁、边缘锯齿和颜色抖动。必须在最终 1080P 环境检查，不以低清 Studio 预览替代成片画质审核。

### 7.2 统一逐帧运动函数

保留原先经过审查的运动数学模型。对逻辑长度为 `N` 的镜头，局部帧 `j∈[0,N-1]`，`u=j/max(1,N-1)`，`e(u)=3u²−2u³`：

```text
z(u)  = z0  + (z1-z0)   * e(u)
ax(u) = ax0 + (ax1-ax0) * e(u)
ay(u) = ay0 + (ay1-ay0) * e(u)
```

其中 `z>=1`、`ax/ay∈[0,1]`。单帧镜头只取起始状态。图片经过 `cover` 预处理后，`transformOrigin: (ax%, ay%)` 配合 `scale(z)`，与原有裁切窗口公式 `x=(iw-iw/z)*ax`、`y=(ih-ih/z)*ay` 对应；局部缩放、焦点平移均由当前帧计算，不使用墙上时钟、随机动画或浏览器自动 CSS transition。

为了使转场前置/后置的保持帧与正常运镜一致，Remotion 内部采用：

```text
head_i = a_(i-1)
tail_i = b_i
physical_i = head_i + N_i + tail_i
sequence_local_frame = useCurrentFrame()   # 处于 TransitionSeries.Sequence 内
logical_local_frame = clamp(sequence_local_frame - head_i, 0, N_i-1)
```

于是前置保持重复镜头首帧，末尾保持重复末帧；仅 `[head_i,head_i+N_i)` 中推进镜头运动。不同转场位置不更改 `N_i` 或镜头运动速度。

### 7.3 静态镜头组件参考实现

以下为待实施的 TypeScript/React 组件示意，不代表当前仓库已有可运行代码：

```tsx
import {AbsoluteFill, Img, staticFile, useCurrentFrame} from 'remotion';

type ShotProps = {
  stagedImage: string;
  headHoldFrames: number;
  logicalFrames: number;
  motion: {
    scale_from: number;
    scale_to: number;
    crop_anchor_from: [number, number];
    crop_anchor_to: [number, number];
  };
};

export const StaticShot = ({stagedImage, headHoldFrames, logicalFrames, motion}: ShotProps) => {
  const local = useCurrentFrame();
  const j = Math.max(0, Math.min(logicalFrames - 1, local - headHoldFrames));
  const u = j / Math.max(1, logicalFrames - 1);
  const e = u * u * (3 - 2 * u);
  const mix = (from: number, to: number) => from + (to - from) * e;
  const z = mix(motion.scale_from, motion.scale_to);
  const ax = mix(motion.crop_anchor_from[0], motion.crop_anchor_to[0]);
  const ay = mix(motion.crop_anchor_from[1], motion.crop_anchor_to[1]);

  return (
    <AbsoluteFill style={{overflow: 'hidden', backgroundColor: '#000'}}>
      <Img
        src={staticFile(stagedImage)}
        style={{
          width: '100%',
          height: '100%',
          objectFit: 'fill',
          transformOrigin: ax * 100 + '% ' + ay * 100 + '%',
          transform: 'scale(' + z + ')',
        }}
      />
    </AbsoluteFill>
  );
};
```

`stagedImage` 只能是 `work/remotion/public` 下的安全图片相对路径，例如 `images/abc123.png`。禁止组件运行时自己查找 Windows 绝对路径，禁止 Remotion 自动从网络生成图片。

## 8. 语义转场、Remotion 整片编排与最终音画封装

### 8.1 AI 语义转场规划器（TransitionPlanner）

转场规划器以**相邻两段旁白、两张通过图片来源/许可与用户效果审查的真实原画及其哈希、当前运镜轨迹、音频语义锚点和停顿**为输入；生成 `relation`、`evidence`、`visual_evidence`、`intent`、`type`、`duration_frames`、`placement`、`planning_source` 和图片摘要。

候选写入 `work/planning/transition_candidates.json`，经确认后成为 `storyboard.json` 的执行来源；图文不一致、未读取原画、擦除方向不确定或语音边界存在歧义时进入 `REVIEW_REQUIRED`。代码只执行通过 Schema 的离散效果标识和整数帧，不能接受 AI 直接生成任意 React/Remotion 代码或注入自定义浏览器脚本。

| 语义关系 | 建议的 Remotion 效果 | 约束 |
|---|---|---|
| 连续叙事、观点反转、直接揭示 | `cut`（相邻 Sequence） | 默认优先，画面在指定帧直接切换 |
| 柔和过渡或现实进入隐喻 | `fade`（内置 `fade()`） | 避免人物双影和过长拖尾 |
| 时间跨越、章节结束 | `fade_black`（自定义 presentation） | 明确黑场表达意图，不添加额外视频时长 |
| 有明确视觉/空间方向 | `wipe_from_left`、`wipe_from_right`（内置 `wipe()`） | 左右方向基于真实画面，与旧 FFmpeg 命名独立 |

Remotion 的 `fade()` 是新镜头逐渐覆盖旧镜头，并非必然两张画面分别按对称透明度变化。`fade_black` 不属于本方案使用的内置效果，需要自行实现：整片最底部固定黑色背景，转场前半段旧画面透明度由 1 降到 0，后半段新画面由 0 升到 1；使用 `@remotion/transitions` 提供的受控自定义 `TransitionPresentation`，并通过首/中/尾帧画面核对是否真正经过黑色。不得直接用普通 `fade()` 冒充黑场转场。

`wipe({direction:'from-left'})` 表示新画面从左侧开始覆盖，`from-right` 同理。枚举不直接接受 `wipeleft/wiperight` 等旧 FFmpeg 名称，需在图像审核后确认具体方向。**语义准确性和旁白时机优于效果多样性**，允许整片只有有理由的硬切；反过来连续显眼特效应触发审美复核。

### 8.2 相对语义锚点的转场位置与整数帧预算

对逻辑边界 `B_(i+1)` 的一处非硬切转场，持续时间 `L_i>0`，前置 `a_i`、后置 `b_i` 满足 `a_i+b_i=L_i`：

| `placement` | `a_i` | `b_i` | 可见转场窗口 |
|---|---:|---:|---|
| `start_at_anchor` | 0 | `L_i` | `[B,B+L_i)` |
| `end_at_anchor` | `L_i` | 0 | `[B-L_i,B)` |
| `center_on_anchor` | `floor(L_i/2)` | `L_i-a_i` | `[B-a_i,B+b_i)` |

`cut` 定义为 `L_i=a_i=b_i=0`。如果真实语音锚点与逻辑边界 `B` 不同，必须记录原因，不能为迁就特效静默改变朗读节奏。

```text
N_i                  = B_(i+1) - B_i
head_hold_frames_i   = a_(i-1)    # 第一镜头为 0
tail_hold_frames_i   = b_i        # 最后一镜头为 0
physical_frames_i    = a_(i-1) + N_i + b_i

transition_start_i   = B_(i+1) - a_i
transition_end_i     = B_(i+1) + b_i
visual_total_frames  = sum(physical_frames_i) - sum(L_i)
                     = sum(N_i) = T
```

边界和持续时间均为整数帧。各转场窗口不得出界，相邻转场不能互相侵入，首版要求：

```text
for every logical shot i:
    b_(i-1) + a_i < N_i
```

该约束保证每个逻辑镜头至少有一帧未处于任意转场窗口，符合 Remotion `TransitionSeries` 不允许相邻转场直接连在一起的约束。对于过短镜头应报告受影响编号和边界，要求修改分镜或人工确认时长，不自动删减动画。

**预算样例：** 三镜头逻辑时长 `120 / 150 / 90` 帧，第一处 12 帧 `end_at_anchor`，第二处 12 帧 `start_at_anchor`：三个序列物理长度为 `120 / 174 / 90`；视觉总时长 `120 + 174 + 90 - 12 - 12 = 360` 帧，恰好 12 秒。两次转场窗口为 `[108,120)`、`[270,282)`；第二镜头真实运镜仍在全局帧 `120` 开始，而不是在其进入第一个转场时提前开始。

### 8.3 Remotion 整片编译器

首版以 `<TransitionSeries>` 作为唯一视觉时间线组合机制，不用 FFmpeg 画面滤镜二次处理，也不用为每个转场生成一段 H.264 再重复压缩。

编译流程：

1. Python 验证 `timeline.lock.json`：镜头顺序、整数帧、每镜头图片的来源及**真实用户批准收据**、许可与哈希、转场窗口、资源存在性、每个镜头物理时长及目标 `T`。
2. 只将图片来源与使用权审核有效、内容哈希匹配的正式静态图复制到项目 `work/remotion/public/images/`；生成只包含受控相对图片路径和执行参数的 `props.json`。
3. Remotion `<Composition>` 使用 `calculateMetadata` 根据受控 `props.video.total_frames` 设置 `durationInFrames=T`，默认画布 1920×1080、30 fps、`ComicVideo` 组件；输入参数须受同一 Schema 约束。
4. 在 `<TransitionSeries>` 中为每个镜头生成一个 `<TransitionSeries.Sequence durationInFrames={physical_frames_i}>`，其中仅渲染一个 `<StaticShot>`。连续两个硬切镜头直接相邻；非 `cut` 边界插入一个 `<TransitionSeries.Transition>`，使用 `linearTiming({durationInFrames:L_i})` 和经过白名单映射的 `fade()`、`wipe()` 或自定义 `fadeBlack()`。
5. `StaticShot` 内通过 `useCurrentFrame()` 获取**序列局部帧号**，扣除 `head_hold_frames` 并限制到 `[0,N_i-1]`，计算图片缩放、裁切焦点和缓动，从而使提前进入的图片先保持首帧、延后结束的镜头保持末帧。
6. 编译前后分别计算 `sum(physical_frames_i)-sum(L_i)=T`；Remotion 输出的 `visual.mp4` 实际帧数、首尾 PTS、关键转场时刻均需由 `ffprobe` 和逐帧解码验证。对非法时长、缺图、组件渲染错误、无图黑帧等立即失败。

Remotion 官方 `TransitionSeries.Transition` 会让两个场景时间区间重叠，并自动缩短整体时长。因此**预留保持帧＋TransitionSeries 重叠**是配音时间线严格对齐的核心。`TransitionSeries.Overlay` 不缩短总时长，不适合在本方案中替代跨镜头叠化。每处硬切边界不要插入持续 0 帧的 `Transition`。

示意结构：

```tsx
<AbsoluteFill style={{backgroundColor: '#000'}}>
  <TransitionSeries>
    <TransitionSeries.Sequence durationInFrames={120}>
      <StaticShot {...shot1} />
    </TransitionSeries.Sequence>
    <TransitionSeries.Transition
      timing={linearTiming({durationInFrames: 12})}
      presentation={fade()}
    />
    <TransitionSeries.Sequence durationInFrames={174}>
      <StaticShot {...shot2} />
    </TransitionSeries.Sequence>
    <TransitionSeries.Transition
      timing={linearTiming({durationInFrames: 12})}
      presentation={wipe({direction: 'from-left'})}
    />
    <TransitionSeries.Sequence durationInFrames={90}>
      <StaticShot {...shot3} />
    </TransitionSeries.Sequence>
  </TransitionSeries>
</AbsoluteFill>
```

实际实现根据数组生成直接子节点，`cut` 时不插入转场节点；`<StaticShot>` 中的 `headHoldFrames`、`logicalFrames` 均由 `props.json` 填入，示例变量省略。每次变更都必须通过编译器检查，而不是直接在 TSX 中手动修补时长。

### 8.4 Remotion 可视化预览与无声视觉轨

Remotion Studio 用于逐帧检查运镜与转场；Studio 的实时视觉预览不等于有声最终审核。需要试听旁白时，先渲染同时间线的无声低清视觉预览，再让 FFmpeg 叠加完整母带，生成 `preview/preview.mp4`。

正式渲染从编译好的参数文件读取数据，避免在 Windows 命令行直接传内联 JSON（容易遇到引号转义）。**进程工作目录必须设为仓库的 `renderer/static-comic/`，使 CLI 使用该目录已安装并由锁文件固定的本地 Remotion 版本**。下例中的尖括号表示编排器传入的真实绝对路径参数，不能直接在 PowerShell 中粘贴执行：

```text
npx remotion render src/index.ts ComicVideo <ABS_VISUAL_MP4> \
  --props=<ABS_PROPS_JSON> \
  --public-dir=<ABS_STAGED_PUBLIC_DIR> \
  --codec=h264 --pixel-format=yuv420p --crf=18 --muted
```

Python 在 Windows 上需正确解析和执行本地 `npx.cmd` / npm 命令入口，使用校验过的参数数组及固定工作目录启动，而不是让 `npx` 在缺少已安装依赖时自行下载任意版本。续行仅用于文档展示；渲染前验证 `calculateMetadata` 返回的时长为 `T`，`--muted` 生成无声视频。Studio 必须从同一版本的 props/素材快照加载，不能将用户手工预览修改隐式当作正式批准的时间线。

低清预览可调整输出分辨率/编码质量，但动画所用逻辑画布比例、帧率、锚点、运镜曲线、转场长度和实际帧位置必须与正式渲染一致；不通过降低帧率加快预览。

### 8.5 FFmpeg 完整音频合成与媒体验证

Remotion 已经输出 H.264 无声 `work/remotion/visual.mp4` 后，FFmpeg **只复制视频流并合成完整配音**：

```bash
ffmpeg -y -i work/remotion/visual.mp4 -i work/audio/master_48k.wav \
  -map 0:v:0 -map 1:a:0 -c:v copy \
  -c:a aac -b:a 192k -ar 48000 \
  -movflags +faststart output/final.mp4
```

不使用 `-shortest`，也不裁掉旁白头尾静音或改变语速。令母带采样数量为 `S`、采样率为 `R`，画面总帧数为 `T`，则视频长度 `T/30` 覆盖 `S/R`，尾部差值必须小于一帧。AAC 编码延迟、填充和容器时长需结合有效播放范围验证；检查音频首尾字词完整。Remotion 视觉轨内不能含有额外音轨，最终仅保留一条视频流、一条音频流且无字幕流。

预览合成使用同一套音画封装逻辑，不对预览音频进行变速或重新切片；正式输出通过流复制避免对高对比二维漫画画面再次有损编码。

## 9. 缓存、重复渲染与可复现性

**Remotion 整片渲染不会自动提供“改一张图片，只重新渲染一个镜头”的视频缓存语义。** 首版明确以下缓存粒度，避免在工程验收中虚假承诺：

| 缓存产物 | 键的主要依据 | 失效与重建行为 |
|---|---|---|
| 音频母带与识别 | 源音频哈希、解码和模型参数 | 配音变化重建，保留受影响证据 |
| 图片渠道/计划与批准 | 已确认的用户渠道方案、逐镜头来源、提示词或检索条件、来源许可、图片审批和哈希 | 选择或许可变动使相应批准及下游视觉语义证据失效 |
| 图片预处理/暂存 | 已批准原图哈希、EXIF/色彩/cover 参数、预处理实现版本 | 仅更新相关暂存图片与清单 |
| 语音对齐 | 母带、原文/读法、窗口、模型版本 | 仅可靠复用输入确实相同的窗口 |
| 锁定时间线 | 原文、已批准分镜、对齐、人工覆盖、编译器版本 | 输入变化后重编译 |
| Remotion 应用构建 | 锁定依赖、源代码、配置、构建环境 | 代码和依赖变化重建 |
| **整片无声视觉轨** | 时间线、全部受引用图片哈希、渲染版本和画质配置 | 任一视觉变化，首版重渲染整条视觉轨 |
| 最终音视频合成 | `visual.mp4` 哈希、母带哈希和音频编码参数 | 若仅音频变化且视觉时间线确实未变，可只重做封装 |
| 预览与审核 | 实际预览、逐镜头图片来源/审批和权利证据、时间线、转场意图与版本 | 图片来源授权变化即使像素不变也须重新审核；视觉或音频变化亦须重审 |

未来如实测表明整片重新渲染成本过高，可再设计基于安全片段边界的 Remotion 分段渲染与缓存。候选技术为 `--frames` / `@remotion/renderer` 对冻结的同一 Composition 做区间渲染，然后 FFmpeg **仅拼接既有视频流、处理音频封装**。该优化必须先验证帧号区间语义、编解码 GOP（图像组）、首尾关键帧、时间戳和带跨片转场的接缝；首版不列为承诺，不在没有证据时宣称局部渲染能够无损直接拼接。

最终文件采用临时路径生成、完整验收后原子替换。发生失败时保留此前有效成片并记录它绑定的旧哈希，不能将旧文件报告为新输入生成。锁定 Python/Node/Remotion/浏览器/FFmpeg/模型版本、源码摘要与配置，保证**逻辑时间线和可见画面状态**可重复；不承诺不同编码器和硬件的 MP4 字节完全相同。

## 10. 工作流、预览与批准机制

未来统一 CLI 可以划分为：

```text
comic-video init <project>             # 询问用户选择供图渠道
comic-video image-plan <project>       # 输出逐镜头提示词/检索任务并确认来源分配
comic-video image-acquire <project>    # 依据已确认渠道执行授权生图或检索
comic-video image-inspect <project>    # 查看候选图和人工放入的图片
comic-video image-approve <project>    # 用户逐镜头或明确批次批准
comic-video validate <project>
comic-video align <project>
comic-video plan-transitions <project>
comic-video timeline <project>
comic-video studio <project>
comic-video preview <project>
comic-video inspect <project>
comic-video approve <project>
comic-video render-visual <project>
comic-video mux <project>
comic-video verify <project>
```

这是一套接口边界，不代表目前已有可执行命令。`studio` 使用本期 `props` 与图片暂存快照打开 Remotion 视觉时间线；`preview` 负责低清视觉渲染与 FFmpeg 有声封装；`render-visual` 生成正式完整无声轨；`mux` 将原始完整配音与其封装。

```text
INPUT_READY → SOURCE_POLICY_PENDING → SOURCE_POLICY_APPROVED
  → STORYBOARD_APPROVED → IMAGE_PLAN_APPROVED
  → IMAGE_CANDIDATES_READY → IMAGE_REVIEW_APPROVED
  → ASSETS_VALIDATED → AUDIO_PREPARED → TIMING_CONFIRMED
  → TRANSITIONS_PLANNED → TIMELINE_LOCKED → REMOTION_ASSETS_STAGED
  → PREVIEW_VISUAL_RENDERED → PREVIEW_AUDIO_MUXED
  → REVIEW_APPROVED → FINAL_VISUAL_RENDERED
  → FINAL_AUDIO_MUXED → OUTPUT_VERIFIED
```

新视频创建后，渠道选择是第一个人工门禁；混合模式需另经逐镜头来源分配确认。音频准备与图片获取在依赖条件满足时可以并行，不要求文字状态序列代表耗时上的串行关系。候选图未经用户批准、缺少第三方发布使用权证据、图片哈希变化时均进入 `REVIEW_REQUIRED`，不得晋级 `IMAGE_REVIEW_APPROVED` 或继续转场规划。对齐、图片语义、渲染或转场窗口异常也进入 `REVIEW_REQUIRED` 并定位镜头及原因。

审核收据绑定：原文、配音、分镜、图片来源选择与混合映射、实际供图提示词/检索来源和授权、逐图人工批准与哈希、人工覆盖、语义规划、锁定时间线、Remotion 源码与依赖版本、预览视觉轨、有声预览哈希。AI 不可以自行批准，渲染成功也不能自动更新批准状态。任何影响成片的输入变化均使相应预览和旧批准失效。

在 Remotion Studio 中可逐帧定位转场开始/结束与镜头运动的起止帧；完整试听则通过 `preview/preview.mp4`，因为本架构的 Remotion 视觉轨本身没有旁白。预览与正式版采用相同帧率、总帧数、逻辑边界、效果类型、运动曲线和转场起止帧；低清仅通过受控的输出缩放与编码质量实现。

## 11. 验收规则

### 11.1 自动技术验证

1. 原文字符区间完整覆盖且保持顺序；原文读法、粗识别、声学对齐、插值与人工修正来源可追溯；误读、漏读、重复句歧义能够触发修复流程。
2. `timeline.lock.json` 逻辑镜头连续覆盖 `[0,T)`，转场窗口合法，不重叠，至少保留每个镜头一个非转场帧；`sum(physical_frames)-sum(transition_frames)=T`。
3. Remotion `calculateMetadata` 的 `durationInFrames`、宽高和 fps 与锁定时间线一致；运行时组件不自行修改片段时长。
4. 所有非 `cut` 使用 `TransitionSeries.Transition` 及正整数 duration；硬切仅串接序列；不使用任意动态特效代码。
5. `visual.mp4` 实际**解码视频帧数为 `T`**、恒定 30 fps、目标像素格式与尺寸，PTS 起点正确且单调连续；无视频间隙、重复外加末帧或额外音轨。
6. 转场必须分别检查 `start_at_anchor`、`end_at_anchor`、`center_on_anchor` 的开始/完成实际帧号；尤其验证提前保持首帧、延后保持尾帧不会拉长镜头自身运动。
7. `cut→fade`、`fade→cut→wipe`、连续两处叠化、全硬切及 `fade_black` 的边界都必须通过帧数与关键帧视觉检查；淡黑必须经过预期的黑色状态。
8. 图片预处理、主体裁切与 `crop_anchor` 从首至末逐帧几何验证；未标注主体时报告“未进行主体检查”，不能假定合格。
9. Python 验证工程路径、图片来源策略、逐镜头审批及授权记录、图片哈希与浏览器公开目录；渠道未确认、图片未批准、非法路径和音频/文本错误公开均被拒绝。
10. 最终 `final.mp4` 一条视频流、一条音频流、无字幕流；与 `visual.mp4` 视频帧内容和参数一致，完整音频保持头尾时长与语速；AAC 延迟/填充单独解释。
11. 重跑完全相同输入复用正确阶段缓存；仅改旁白但画面时间线未变时视觉轨可复用；改任一图片/运镜/转场时首版整片视觉轨重建，不虚报单镜头视频缓存。
12. 同步报告**图片来源许可与人工审图**、技术检查、语义规划检查、完整试听和正式画质五类状态；未执行只能记录 `NOT_RUN` 或 `UNAVAILABLE`，不得记录为 `PASS`。
13. 本地生成、第三方检索、人工放图及混合来源均有可复核的来源选择、候选、批准与驳回用例；人工放置或模型返回文件不自动获得 `APPROVED`。

### 11.2 人工视觉与叙事验收

- 对照原文完整观看：重要概念出现时画面已经处于预期呈现状态；镜头提前/延后混合有合理语义依据。
- 分镜可以有人物，也可以是纯物体或空间隐喻；渲染不强制添加人物，画风仅依赖已审核图片本身。
- 运动自然，人体、道具、隐喻主体无裁切；慢推高对比线条不明显闪烁、振铃或变软。
- 淡入、黑场与左右方向擦除有叙事理由；允许全片硬切，不以特效数量评价成片。
- 人工试听原始配音首尾没有吞字或提前截断；完成视频没有自动字幕、镜头编号或审核文字。
- 正式画质审核和低清预览批准分开记录，低清通过不意味着1080P画质自动通过。

## 12. 最小样片验证计划

### 12.1 样片规格与设计覆盖

制作一条 **60～90 秒、8～12 镜头、单文件真实中文配音**的测试项目。**项目开始即确认图片供图渠道**，按照各镜头确认的渠道完成候选获取、来源/许可核对和逐张人工批准；测试分支覆盖本地生图、授权图库检索与人工提示词供图，混合模式验证至少两种同片共存。配音覆盖数字/百分比、重复短句、术语、头尾静音、长停顿及语义反转；画面包含人物、纯隐喻、边缘主体、非 16:9 原图和漫画细线。

真实样片的特效由内容决定，不为测试效果强行安排特效；另外独立制作彩色块/编号测试夹具覆盖全部五类首版效果、三种 `placement`、长短不同的镜头及非法转场窗口。

### 12.2 逐阶段验证矩阵

| 阶段 | 验证内容 | 必须保留证据 |
|---|---|---|
| A：环境 | 确认 Node、Remotion、React、浏览器、FFmpeg、WhisperX 安装及许可；锁定依赖 | 版本、平台、锁文件、命令、状态 |
| B：运动探针 | 单图片居中推近/拉远、移动焦点、水平/纵向平移、缓入缓出 | 原图、逐帧期望值、渲染帧 |
| C：转场探针 | `TransitionSeries` 全硬切与混合序列、三类 `placement`、自定义淡黑 | 起止边界、逐帧图、真实帧数 |
| D：图片供应与审图 | 用户来源确认、三渠道分支、混合镜头方案、候选图和人工审批、许可及风格 | 提示词、原始来源、授权凭据、逐图哈希与批准/驳回记录 |
| E：完整语音 | 配音解码、粗识别、原文/读法对齐、人工修正异常 | 声学对齐、采样位置、异常报告 |
| F：语义编排 | AI 检查已批准真实原画、运镜和口播锚点，确定转场类型及持续时间 | 图片审批、视觉证据、候选计划、人工确认 |
| G：整片预览 | Remotion 无声预览与 FFmpeg 有声预览，审核故事节奏 | 锁定时间线、双预览、联系表、收据 |
| H：正式输出 | Remotion 1080p `visual.mp4` + FFmpeg 完整音轨封装 | 逐帧检查、ffprobe、final.mp4、人工观看 |
| I：复现与失效 | 原样重跑、图片/来源/许可变更、仅修改配音、转场位置变更 | 缓存命中、图片批准和无声轨失效证据 |

### 12.3 关键回归测试

**时间预算测试：**

```text
logical_shots = [120, 150, 90]
transition_0 = {type: "fade", duration: 12, placement: "end_at_anchor"}
transition_1 = {type: "wipe_from_left", duration: 12, placement: "start_at_anchor"}
physical_shots = [120, 174, 90]
expected_total_frames = 120 + 174 + 90 - 12 - 12 = 360
expected_windows = [[108,120], [270,282]]
```

用真实 Remotion Composition 证明帧数恰为 360，第一处转场第 120 帧已经完整切换，第二处从第 270 帧开始；第 120 帧开始第二镜头正常运动，末尾保持不会产生额外的动态缩放。

**媒体边界测试：** 11.981 秒的母带搭配 360 帧、30 fps 无声视觉轨，混流后音轨完整，视频仍为 360 帧。最终不得因 `-shortest`、AAC 编码尾帧或默认导出参数而改变视觉长度。

**失败与纠错测试：** 图片渠道未确认、混合镜头来源未批准、本地生成工具不可用、第三方许可凭据缺失、候选被驳回、人工图片尚未放置/被替换、已批准图片被覆盖、重复句错配、粗时间回退、真实漏读、非法 `script_range`、非法 Windows 路径、转场窗口重合、`fade_black` 未经黑场、旧预览批准误复用，均须阻止错误放行并提供定位。

**缓存真实性测试：** 删除整片 `visual.mp4` 后生成完整结果；更换一张图时，本阶段会重渲染整片视觉轨；只变配音而逻辑镜头及视觉输入的哈希完全一致时，可复用既有无声视觉轨并重新封装配音。

**性能测试：** 在同一台 Windows 电脑上记录 1 分钟和 3 分钟片长的全程渲染耗时、峰值内存、浏览器进程数量、CPU/GPU 占用及高对比线条画质，作为后续是否建设分段渲染缓存的依据。

### 12.4 通过条件与停止策略

先完成技术探针，再进行真实样片。成功标准是：**来源策略经用户确认、每张入镜图片的许可与效果得到人工批准**、音频对应的 `T` 帧完整、镜头视觉时间点正确、无声轨与最终有声视频内容一致、人工认可画风/镜头/转场/完整试听。语音对齐异常必须定位后修复，不能靠臆造精度或截断音频绕过。

分别记录 `PASS`、`FAIL`、`NOT_RUN`、`UNAVAILABLE`。若中文语音需要大量人工纠正，先改善对齐与校正入口；若性能瓶颈显著，再设计分段缓存。未经技术验证与人工样片审核，不开始批量生产。

字幕、背景音乐、口型、多轨道和复杂特效都不是本文的既定功能。
