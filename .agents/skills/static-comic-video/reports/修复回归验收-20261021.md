## 1. Windows 进程边界路径

根因：Python 可接受的 Windows 扩展路径被直接传给 Node 入口、cwd 和参数；Node 的部分路径解析无法处理该表示。只修改 cwd 不能覆盖入口脚本、props、public、浏览器及输出路径。

实际修复：

- `static_comic/paths.py:process_path/process_args` 统一将已授权的本地扩展盘符路径转为原生盘符路径，保留中文、空格和参数边界。支持独立路径参数及 `--flag=path`。
- `media.run`、`doctor.run`、`delivery.studio` 共用适配；`delivery.runtime` 统一浏览器路径。构建、预览和正式视觉渲染经过 `media.run`；Studio 的 Popen 也使用同一适配。
- `resolve_path` 原有相对路径、越界符号链接及路径穿越检查继续有效；适配层拒绝 UNC、扩展 UNC、设备命名空间和显式盘符相对路径，不承担资源授权。
- 保持 argv 调用，没有 `shell=True`。FFmpeg 的 `a:0`、`0:v:0`、过滤表达式等不是路径，保持原值。
- 适配覆盖 Node/Remotion 与 `media` 的封装/验证调用；原有 `speech_audio.prepare_audio` 的直接 FFmpeg 调用未重构，真实扩展路径探针亦成功经过该准备阶段。

修复前：扩展路径会在 Node 入口解析阶段失败。修复后：同一套生产调用路径可处理两种表示，保留原有访问边界。

## 2. 人工确认入口与审批绑定

根因：原 `check_human` 仅检查调用者声明的身份、时间和 evidence；其格式有效不等于经过用户确认。

实际修复：

- 新增 `static_comic/human_review.py` 和 `human-confirm` CLI。用户在交互式终端核对完整决定与对象摘要，输入指定确认短语；管道、非交互输入或取消不签发收据，无自动同意选项。
- 首次交互在当前账户项目外生成密钥。HMAC-SHA256 绑定来源 `local_terminal`、scope、完整决定、账户和时间。Agent 准备建议；交互入口签发；原 confirm/review/approve 接口复验并应用。三个职责分离。
- `project.check_human` 验证签名、作用域及负载；图片、来源、分镜计划、转场、有声预览和正式画质均接入。许可字段、几何、语义和当前资源摘要仍独立检查，签名不能覆盖这些失败。
- 图片批准不仅绑定公开摘要，还读取 `record_sha256` 指向的历史供应事件，核验该事件摘要和当前完整候选/来源/许可相等。重写许可证并重新计算公开摘要，仍不能沿用旧批准。
- 对同一候选转场边界、同一 stage/binding 媒体决定，精确重复幂等；旧 APPROVED 不能覆盖较新 REJECTED。重新批准须有新的有效确认。
- 旧版无签名或不可验证的画质记录返回 `REVIEW_REQUIRED`、`production_accepted=false`，但不阻塞技术核验及用户重新确认。更新前将旧记录原字节保存到 `review/delivery-history/<hash>.json`。
- `schemas/contracts.json` 与生成的 TypeScript 契约同步；旧记录仍可读取，但不能通过新生产门禁。`speech_text` 的 reading/boundary 历史注释仍使用 `check_human_metadata`，不视为生产批准，也不能代替完整试听。

修复前：任意 evidence 字符串配合 human 字段可能放行。修复后：缺少有效本地签名、签名被改动、对象过期、跨审批阶段或正常 API 重放旧批准均拒绝；候选、来源和媒体替换必须重新确认。

这不是不可伪造的真人认证。同一 OS 账户的恶意程序可读取密钥、改代码或控制终端；终端不能证明用户确实看图或听完。收据绑定内容而非目录名称，复制完全相同对象到同账户的其他目录不会单凭路径变化失效。详见 `references/human-confirmation.md`。本次自动测试只使用临时密钥和模拟交互，没有签发真实用户批准。

## 3. 来源策略查询状态

根因：`policy_options()` 以 confirmation 存在与否选择提示，没有复用批准校验，还在查询时创建默认策略，导致查询与确认负载混淆。

实际修复：

- 查询只读，不创建或重写文件；初始化由 `delivery.initialize` 显式完成。
- 无选择返回 `SOURCE_POLICY_PENDING`；有效签名、负载、配置和逐镜头映射一致时返回 `APPROVED`，直接带回 mode、allowed_channels、default_channel 和完整 shots 映射。
- 配置变更、收据过期或不可验证返回 `REVIEW_REQUIRED`。摘要以待批准状态构造，不修改磁盘记录。
- 已有当前请求的实际供应失败可在对应渠道报告 `UNAVAILABLE`；未探测为 `NOT_PROBED`，不把许可批准等同于渠道在线，也不因查询触发生图或网络调用。

单渠道、混合模式、重复查询、配置改变、伪造/过期确认及原 confirm-policy/confirm-plan 均有回归覆盖。

## 4. 图片晋级文件一致性

根因：正式图片、manifest、供应状态和审核记录先后直接写入，中途失败可能混合新旧版本。

实际修复：

- `image_supply.write_docs` 统一经 `cache.publish` 发布，不维护第二套替换机制。
- `review` 先校验整批候选、来源许可、几何、审核字段、输出路径及全部文档形状；读取实际图片字节后再次验证内容摘要，再开始发布。
- `cache.publish` 先准备所有临时文件并校验内容，逐文件 `os.replace`，保留旧字节用于可捕获异常回滚；创建目录后及替换前重新解析目标路径。
- 回滚失败保留原始 `.bak` 并明确报告恢复不完整，避免删除仅剩的旧内容。重试可完成合法发布；缓存命中也须经过批准/清单/实际文件的一致性校验。
- 批次预检失败或替换中途失败不撤销其他镜头既有有效批准；替换、拒绝与重新生成保留历史事件，并要求新候选重新审图。

多文件发布没有真正的跨文件断电原子事务保证，也不新增并发写入协议。进程被强制终止后的混合状态通过文件摘要、manifest、历史事件和批准绑定检测并阻断；需恢复文件或重新执行合法审核/发布，不能靠缓存绕过。
